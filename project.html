Team capstone · 60% of grade

Course Project

The capstone is a candidate-matching platform. In teams of three, build a working full-stack web app to a fixed specification — candidates and employers, authentication, a deterministic match score, and interview scheduling with no double-booking. Then go public, audit another team's build for the vulnerabilities you were taught to find, and defend your system in a live demo.

Spec-first, agent-built

You are given the requirements. Turn them into a SPEC.md, then drive coding agents to implement it — while you stay accountable for every line that ships.

Adversarial peer audit

At feature freeze you go public. Another team clones your repo from a clean checkout and hunts for SQL injection, XSS, and broken booking concurrency.

Defend it live

Demo the running system, walk your architecture, and answer for the audit findings against you. Working software and a clear defense both count.

Specification · FP-*

Project Requirements

What the product must do. Every requirement carries a stable ID so tests and the peer audit can trace back to it. This is the graded contract — the full REQUIREMENTS.md in the starter repo is authoritative.

AreaIDsRequirement
ArchitectureFP-ARCH-1A full-stack web app with a persistent database, runnable from a clean checkout with documented install steps.
AuthFP-AUTH-1/2/3Register, log in, and log out; passwords stored only as salted hashes; sessions scoped to the two roles — candidate and employer.
CandidateFP-CAN-1/2/3Candidates create and edit a profile, list their skills, and browse open positions.
EmployerFP-EMP-1/2/3Employers post and edit job openings with required skills, and view matched candidates for a role.
MatchingFP-MATCH-1/2A deterministic match score from the overlap of candidate skills and role requirements — same inputs, same score, every time.
SchedulingFP-SCHED-1/2/3Book, view, and cancel interview slots; a slot can never be double-booked, even under concurrent requests.
SecurityFP-SEC-1/2/3/4Defend against SQL injection and XSS, enforce authorization on every route, and keep secrets out of the repo.
ProcessFP-PROC-1/2Continuous integration runs the full test suite from a clean checkout; work is tagged at feature freeze.
DocsFP-DOC-1/2/3Ship SPEC.md, INSTALL.md, README.md, and an AI_USAGE.md recording how AI was used.
TestingFP-TEST-1Automated tests covering the requirements — including atomic booking and the security defenses above.

FP-MATCH · the scoring contract

# Deterministic. No LLM, no randomness — the audit will pin this exactly. def match_score(candidate_skills, role_requirements): C, R = set(candidate_skills), set(role_requirements) if not R: return 100 # a role with no requirements matches everyone return 100 * len(C & R) // len(R) # {Python, SQL} vs {Python, SQL} -> 100 # {Python} vs {Python, SQL} -> 50 # {Rust} vs {Python, SQL} -> 0
Milestones

Project Milestones

Build, freeze, audit, defend. The capstone runs through the back half of the term. Dates track the course calendar; the official course site is authoritative if they differ.

Weeks 6–11 · Build

Spec & implementation

Form teams of three, write SPEC.md from the requirements, stand up CI early, and build feature by feature with agents in the loop. Keep AI_USAGE.md current as you go.

Week 11 · Feature freeze

Green CI, tag v1.0-audit

All requirement-level tests pass from a clean checkout. Push the freeze tag — this is the exact commit another team will audit. No new features after the tag.

Week 12 · Competition

Go public & audit a peer

Repositories go public. You clone your assigned team's tagged commit, attempt SQL-injection / XSS / double-booking exploits, and file a written audit that cites the FP-* IDs at issue. Confirm findings against you and repair.

Weeks 13–14 · Presentations

Demo & defense

Demo the running system live, walk the architecture and your AI-usage story, and respond to the audit findings — what was real, what was fixed, what you dispute.

Capstone rubric · 100 pts

Project Grading

How the capstone is scored. The project's internal 100 points split three ways. Working, spec-compliant software carries the most weight, but a rigorous audit of another team and a strong live defense are graded in their own right.

Requirements fulfillment spec-compliant, tested, green CI40
Peer review quality of the audit you perform + how your build holds up40
Presentation live demo + architecture & audit defense20

Non-negotiables. No real secrets in the repository — commit an .env.example with placeholders only. The suite must include an atomic-booking concurrency test and explicit SQL-injection and XSS tests, and everything must pass in CI from a clean checkout. A build that only runs on your laptop does not count.
